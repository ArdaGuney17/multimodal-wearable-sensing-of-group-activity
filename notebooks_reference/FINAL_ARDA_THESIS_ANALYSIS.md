### 1. Per-group sync mechanism

**Yes — this notebook computes a genuine per-group time-alignment ("sync shift") between the OpenEarable/Xsens sensor timelines and the ELAN annotation timeline, for all 9 study groups, with a shared core algorithm applied with per-group hand-tuning.** This is present nowhere else that has been analyzed in this repo so far.

**Core algorithm (quoted, from `CELL 66`, lines 10209-10247 — Group 5's Xsens shift, representative of the pattern used everywhere):**
```python
def find_xsens_peak_near_clap(df):
    ...
    sync_start, sync_end, _ = find_label_segment(df, TIME_COL, SYNC_LABEL_COL, SYNC_LABEL)
    sync_middle = (sync_start + sync_end) / 2
    # Use P3 signal for peak detection
    signal = acc_mag_xsens(df, PEAK_USER)
    search_left = sync_start - SEARCH_BEFORE_SYNC_S
    search_right = sync_end + SEARCH_AFTER_SYNC_S
    mask = (times >= search_left) & (times <= search_right)
    local_idx = np.where(mask)[0]
    peak_idx = local_idx[np.nanargmax(signal[mask])]
    peak_time = times[peak_idx]
    offset_sec = peak_time - sync_middle
    ...
```
i.e.: (1) locate a **designated ELAN annotation label** acting as a synchronization anchor — the tier `label_Whole_Group`, label text `"synchronizaiton_move"` (this exact typo, verbatim, throughout the file) or `"clap_synchronizaiton_move"` for some groups; (2) take that label segment's midpoint; (3) compute the combined (participant-averaged, or single-participant) accelerometer-magnitude signal and find its **highest local peak inside a search window around that midpoint** (the physical event is a synchronized clap/motion gesture performed by participants at a known point in the session, meant to be visible as a sharp acceleration spike in the raw sensor data); (4) `offset_sec = peak_time - label_middle`; (5) shift **every** ELAN label segment (all 7 tiers: `Participant1/2/3`, the 3 pairs, `Whole_Group`) by that same `offset_sec` and re-derive the `label_*` columns on the sensor time grid. The label-segment extraction (`get_label_segments`), the shift application (`shift_all_labels`/`shift_label_column`), and this peak-alignment routine are re-implemented near-identically (copy-paste, not shared imports) in essentially every group's shift cell — the same duplication pattern documented in the two template analyses for this repo's other large notebooks.

## Summary

This is a **raw-data synchronization and ELAN-labeling notebook**, not a feature-engineering or modeling notebook — it contains zero `sklearn`/`torch` imports and never trains or evaluates anything. Structured as 9 near-identical per-group blocks (Groups 1, 2, 3, 5, 6, 7, 8, 9, 10 — Group 4 excluded throughout, consistent with the rest of the thesis codebase), each block: (1) merges each participant's raw OpenEarable 8-stream sensor files onto a shared 50 Hz grid and raw Xsens 9-column files onto a shared ~30 Hz grid; (2) reads the group's **raw, real-participant-name** ELAN annotation export, synthesizes a pre-collaboration `"individual_build"` label in each participant's early per-tier gaps, then renames real names to canonical `Participant1/2/3` (+ pair + `Whole_Group`) tiers, producing the exact `Group_N_individual_build_renamed.csv` files already flagged in `docs/data_provenance.md` as the anonymized, publishable variant; (3) merge-`asof`s those renamed labels onto both sensor grids; (4) for most groups, detects a designated `synchronizaiton_move`/`clap_synchronizaiton_move` ELAN annotation and computes a peak-alignment time-shift by finding the nearest strong accelerometer-magnitude burst (a physical clap/sync gesture) and re-painting all label columns at the corrected offset — with substantial per-group hand-tuning (which participant(s)' signal to trust, which of several sync-label occurrences to use, manually-read-off-a-plot search windows for Group 6, a separate hardcoded device-start-time correction for Group 7, and an "early common peak" override for Group 9 where the official ELAN tag turned out to be wrong). This is a **new, more complete sync mechanism than any previously-analyzed notebook in this repo** (prior findings covered Group 1 only), and its output filenames are a byte-for-byte match against what `src/preprocessing/global_cleaning.py` already hardcodes as its assumed-fixed input — meaning **this notebook is very likely the actual origin of those files, resolving the "Raw sensor sync" gap** in `docs/table_to_source_mapping.md`, modulo (a) 4 specific (group, sensor) files where this notebook's own final dashboard cell disagrees with what the repo currently selects, (b) no OptiTrack coverage at all, and (c) missing execution evidence for over half the notebook's cells (Groups 1/2/3/5/6). **It does not, however, resolve the separate Task-1 5-second window/label-grid circularity** documented for `master_feature_generator_task1_task2_task3_CORRECTED_V4.ipynb` — this notebook never builds a windowed grid or a binary interaction/non-interaction label anywhere; it stops at producing sample-rate-native, ELAN-labeled, time-corrected per-group sensor CSVs, which is exactly the *input* the windowing/feature-engineering stage still needs but does not itself construct from scratch. A future porter should treat this notebook as the (previously missing) source for `src/preprocessing/global_cleaning.py`'s upstream stage, resolve the 4-file discrepancy and the "long"/Group-1-raw-file anonymization follow-ups by hand with the thesis author, and continue treating the Task-1 window-grid bootstrap as a still-open gap.
